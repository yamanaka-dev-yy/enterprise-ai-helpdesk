# Issue・PR・マージの運用ルール

変更の目的・実装・検証結果を追跡できるように，通常の変更は「Issue → 作業ブランチ → PR → 検証とレビュー → マージ」の順で進めます．機能追加・不具合修正・設定変更・ドキュメント整備を対象とします．

## Issueを作成する

作業前に既存のIssue・PRを確認し，同じ目的のものがあれば継続して使います．新規作成時はタイトルに解決したい問題を記載し，本文に次をまとめます．

- 背景と目的．
- 対応する範囲と，今回扱わない範囲．
- 動作や資料で確認できる完了条件．
- 必要な検証と，未解決の確認事項．

通常のタスクには「開発・改善タスク」，不具合には「不具合報告」のIssueフォームを使用します．CLIなどから作成するときも同等の項目を記載します．秘密情報や実際の社内資料をIssueへ貼りません．

## 作業ブランチで対応する

作業ツリーと最新の `main` を確認し，ユーザーの未コミット変更を上書きしません．通常の作業を `main` へ直接pushせず，Issue番号を含むブランチを作成します．

```text
feat/issue-番号-短い説明
fix/issue-番号-短い説明
docs/issue-番号-短い説明
chore/issue-番号-短い説明
```

一つのPRは一つの目的に絞り，関係のない変更を混ぜません．コミットには変更内容と理由が分かる名前を付けます．

## PRを作成する

ベースブランチは `main` とし，次を記載します．

- 解決する問題と，変更後の動作．
- 主な変更内容と，対応するIssue．
- 実行した検証コマンド・結果と，未実行の検証．
- 制約・残る課題と，マージを任せるかユーザー確認を待つかの扱い．

IssueをこのPRで完了させる場合は，本文に `Closes #番号` を記載します．一部のみ対応するPRでは `Refs #番号` とし，未完了のIssueを自動クローズしません．未完成の場合はDraft PRにします．

## 検証とレビュー

変更に応じた検証を実行します．次は標準の確認コマンドです．変更と無関係な検証を実施したことにせず，未実行は理由とともに記録します．

```sh
.venv/bin/python -m pytest backend/tests -q
.venv/bin/ruff check backend scripts
python3 scripts/sync_docs.py
python3 scripts/sync_docs.py --check
cd frontend
npm run typecheck
npm run build
```

ソース変更に影響する設計・制約・評価の説明も更新します．ドキュメントの句読点は「，」「．」に統一し，READMEには応募先などの実在企業名を記載しません．生成ファイルは手動で編集しません．

PRの差分を確認し，目的との一致，認証・権限制御，秘密情報，後方互換性，必要なテスト，説明の正確さをレビューします．個人開発で自己レビューを行った場合はその旨を記録し，独立したレビュー担当者の承認があったとは表現しません．

現在のPR用CIでは `backend`，`frontend`，`container`，`docs-check` の成功を確認します．PRでは `docs-sync` は実行条件によるスキップが正常です．CIのエラーをスキップ扱いに変更してマージしてはいけません．検証に失敗した場合は修正して再確認します．

## マージの条件

次の全てを満たした場合だけマージします．

1. Issueの完了条件を満たし，PRの差分レビューに未解決の問題がない．
2. マージ対象の最新コミットに対して必要なCIが成功している．
3. コンフリクトがなく，対象ブランチと差分が確認した内容から変わっていない．
4. ユーザーがその作業のマージまで許可している．

同じ依頼で「問題がなければマージまで」と許可されていれば，条件を満たした後に再度確認を求めず進めます．別の依頼や将来の全てのPRへの無条件のマージ許可とは扱いません．継続的なマージ運用を明示的に任された場合は，その合意した範囲に従います．

標準はSquash mergeです．CLIでは確認済みのhead SHAを `--match-head-commit` で指定し，別のコミットに変わっていたら停止して再確認します．ベースブランチの変更で検証結果が古くなった場合も，必要な取り込みと再検証を行います．管理者権限によるCI・保護ルールの迂回や，force pushは行いません．

マージ後はPRが `MERGED` であることと，完了したIssueのクローズを確認します．関連Issue・PR・実行結果へのリンクを報告し，ローカルの `main` を同期します．作業ブランチの整理はマージ済みの今回のブランチに限定します．

## ドキュメント自動更新の例外

既存の `docs-sync` による `github-actions[bot]` の自動コミットは，生成領域と句読点の同期に限定した例外として `main` への直接更新を許可します．手書きの設計変更・コード変更をこの例外で直接反映してはいけません．

botの自動コミットに付ける `[skip ci]` は，ドキュメントだけの再実行を避ける目的です．通常の作業PRと，そのマージコミットには付けません．詳細は [ドキュメントの更新](documentation.md) を参照してください．

この文書とテンプレートは開発時の運用ルールです．GitHub側のブランチ保護やルールセットを自動設定するものではありません．保護を追加する場合は，ドキュメント自動更新との整合も別途確認します．
