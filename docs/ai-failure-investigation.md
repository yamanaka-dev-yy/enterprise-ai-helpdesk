# 生成AIの障害調査と対策

## 調査結果

2026-11-09の公開評価では，管理者の「管理者用緊急対応コード」への生成が25,328.86ms後に `provider_error` となり，本文抜粋へ切り替わりました．当時のコードは `httpx.Client(timeout=25)` で，HTTP障害とJSON等の応答形式不正を同じ例外処理にまとめていました．

25秒の待ち時間と実測値が近いため，応答待ちタイムアウトが有力な仮説です．ただし，当時は例外種別・HTTPステータスを保存しておらず，プロバイダーのログも未取得なので，過去の原因は確定できません．管理者向け資料の内容が原因だった，APIキーが不正だった，無料枠が尽きた，と断定できる記録はありません．この1件だけで資料やモデルを変更していません．当時の評価記録はPR #10，追試の管理はIssue #4で行います．

## 実装した対策

- 接続待ち5秒，応答待ち45秒，送信待ち10秒，接続プール待ち5秒に分けました．応答待ちは `LLM_READ_TIMEOUT_SECONDS` で変更でき，5〜60秒に制限します．待ち時間を延ばせば必ず成功するという意味ではありません．これらは各処理の待ち時間であり，要求全体が45秒以内に終わる保証ではありません．
- 障害時には既存の `reason=provider_error` を維持し，追加の `failure_code` で分類します．タイムアウト時には待ち時間超過を画面の説明にも表示し，閲覧権限内の本文抜粋へ切り替えます．
- サーバーログには分類，処理段階，所要時間，HTTPステータスだけを記録します．処理段階は `generation` または `embedding` です．URL，キー，質問，レスポンス本文，例外全文を出力しません．監査ログには固定の分類イベントだけを残します．
- 自動再試行は追加しません．1回の生成処理の失敗で追加の呼び出しを発生させず，利用回数にも失敗を含めます．Embeddingが有効な場合に別の埋め込み要求が行われる点は従来どおりです．
- 応答全体や回答JSONが配列など想定外の形式だった場合も，エラーとして抜粋へ切り替えるようにしました．出典IDを確認できない場合の既存の回答保留は維持します．

| failure_code | 判別する状態 |
|---|---|
| read_timeout | 応答読み取りのタイムアウト |
| connect_timeout | 接続時のタイムアウト |
| other_timeout | 送信や接続プール待ちなどのタイムアウト |
| authentication | HTTP 401または403．認証・権限等の拒否であり，キー不正だけを意味しない |
| rate_limit | HTTP 429．プロバイダー側のレート・割当制限等 |
| provider_server | HTTP 5xx |
| http_status | その他のHTTPエラー |
| network | タイムアウトやHTTPステータス以外の通信エラー |
| invalid_response | JSONや応答構造，数値形式などの不正 |

ログの形は次のとおりです．値は説明用の例で，実公開の再発ログではありません．

```text
ai_failure category=read_timeout stage=generation elapsed_ms=45000 http_status=None
```

`failure_code` はAPIで取得できます．管理者デモでは他の訪問者の監査ログを見られないため，詳細な運用調査にはサーバーログを使います．通常管理者の監査イベントには質問本文や秘密情報を含めません．設定変更のためにAPIキーをチャットやIssueへ貼る必要はありません．

## 検証した範囲

ローカルでバックエンドテスト62件，Ruff，ドキュメント同期を確認しました．例外分類，秘密情報の非記録，失敗時1回だけの呼び出し，利用履歴のエラー記録，接続・読み取りの待ち時間設定と制限，応答形式不正，Embedding段階の障害分類をモックで再現しています．実際に45秒待つテストや実プロバイダーの成功確認ではありません．

今回の修正はPRでレビューする段階であり，公開デモにはまだ反映していません．公開反映後は利用上限内で管理者向けの1問を追試し，回答または固定の障害分類を記録します．過去の失敗記録を成功結果で上書きせず，別の評価結果として保存します．プロバイダーの一時的な遅延や障害そのものを解消したとは主張しません．
